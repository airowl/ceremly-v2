# R2 Storage Code Review Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Execute the multi-agent R2 storage code review defined in `docs/superpowers/specs/2026-07-11-r2-code-review-design.md`, produce a verified findings report, and hand off a TDD fix plan for the selected findings.

**Architecture:** Two-stage. Stage A (this plan): inline scout → one Workflow run (5 parallel lens reviewers → code dedup → adversarial verify with 3 votes for P0/P1) → findings report committed to `docs/reviews/` → user gate on fix selection. Stage B (generated by Task 5, not pre-written here because fixes depend on findings that don't exist yet): a second plan `docs/superpowers/plans/2026-07-11-r2-fixes.md` with one TDD task per selected fix.

**Tech Stack:** Claude Code Workflow tool (multi-agent orchestration), Vitest (fix stage), git on branch `dev`.

## Global Constraints

- Branch: `dev`. Auto-commit ok, **push always manual** (project convention).
- Report file: `docs/reviews/CODE-REVIEW-R2-2026-07-11.md` (exact path from spec).
- Severity scale: P0 blocker (security breach / data loss), P1 real bug high impact, P2 should-fix, P3 minor.
- No unverified P0/P1 may appear in the report's confirmed section (3-vote adversarial verify, majority).
- Uncertain findings go to a "manual verification" report section and never into the fix plan.
- Fix plan scope: all P0, all P1, P2 only if high-impact/low-cost (user gate decides).
- `server/services/dataExport.service.ts` is modified in the working tree: review the **working-tree version**; never stage or commit that file in this plan.
- Docs/comments in English (project language convention).
- No code fixes during Stage A — review only.

- [ ] **Step 1: Invoke the Workflow tool** with `args: { context: "<full content of r2-scout-context.md>" }` and this exact script:

```javascript
export const meta = {
  name: 'r2-code-review',
  description: 'R2 storage review: 5 lenses, dedup, adversarial verify',
  phases: [
    { title: 'Find', detail: '5 parallel lens reviewers' },
    { title: 'Verify', detail: 'adversarial skeptics, 3 votes for P0/P1' },
  ],
}

const FINDINGS_SCHEMA = {
  type: 'object',
  required: ['lens', 'verdict', 'findings'],
  properties: {
    lens: { type: 'string' },
    verdict: { enum: ['clean', 'findings'] },
    findings: {
      type: 'array',
      items: {
        type: 'object',
        required: ['title', 'file', 'line', 'severity', 'description', 'failureScenario', 'recommendedFix'],
        properties: {
          title: { type: 'string' },
          file: { type: 'string' },
          line: { type: 'integer' },
          severity: { enum: ['P0', 'P1', 'P2', 'P3'] },
          description: { type: 'string' },
          failureScenario: { type: 'string' },
          recommendedFix: { type: 'string' },
        },
      },
    },
  },
}

const VERDICT_SCHEMA = {
  type: 'object',
  required: ['verdict', 'reasoning'],
  properties: {
    verdict: { enum: ['confirmed', 'refuted', 'uncertain'] },
    reasoning: { type: 'string' },
    adjustedSeverity: { enum: ['P0', 'P1', 'P2', 'P3'] },
  },
}

const CONTEXT = args.context

const BASE = `You are a senior code reviewer examining the Cloudflare R2 storage integration of a Nuxt 4 multi-tenant SaaS (Vercel serverless, Neon Postgres via Drizzle, Better Auth organizations, Upstash QStash).

${CONTEXT}

Read ALL perimeter files with the Read tool (absolute paths = repo root + relative path). Follow imports when needed to understand behavior. Review ONLY through your assigned lens. Report findings with exact repo-relative file paths and 1-indexed line numbers. Severity: P0 blocker (security breach / data loss), P1 real bug high impact, P2 should-fix, P3 minor. Only report real, code-evidenced issues — no style nits, no speculation, no duplicates of the "do not re-report" items in the context. If your lens finds nothing, verdict "clean" with empty findings.

YOUR LENS: `

const LENSES = [
  {
    key: 'security',
    prompt: BASE + `MULTI-TENANT SECURITY. Check: (1) every file DB query filters by organizationId — including url.get, delete, confirm, cleanup, gdpr purge; (2) presigned upload URLs: scope, expiry, content-type and content-length pinning, can a presign for org A write into org B's key space; (3) object key construction: path traversal or injection via user-controlled filename/id; (4) presigned download URLs: can a user mint URLs for files of another org; (5) magic-bytes validation: bypass routes (presign flow vs direct upload — is validation enforced on BOTH paths, including after confirm); (6) public vs private object exposure (getObjectUrl/getUrl); (7) authz on the admin/cron cleanup endpoints. Set lens to "security".`,
  },
  {
    key: 'correctness',
    prompt: BASE + `CORRECTNESS & ROBUSTNESS. Check: (1) orphan states — R2 upload succeeded but DB insert failed, and DB row exists but object missing; who reconciles, does cleanup.ts actually catch every orphan class; (2) SHA-256 dedup: hash collisions across orgs, dedup + delete interaction (deleting a deduped file another row still references), dedup on presign flow where the server never saw the bytes; (3) presign→confirm TOCTOU: confirm before upload finished, confirm with wrong size/hash, double confirm, never-confirmed rows; (4) delete flow: DB-first vs bucket-first ordering, partial failure; (5) image variant pipeline: variant generated for a file deleted meanwhile; (6) error handling: swallowed errors, missing 23505 handling, retries on transient R2 errors. Set lens to "correctness".`,
  },
  {
    key: 'cost-perf',
    prompt: BASE + `COST & PERFORMANCE (R2 pricing: Class A ops = writes/lists, Class B = reads, egress free to internet but ops billed). Check: (1) redundant HEAD/GET/exists() calls per request path; (2) presigned download vs public bucket URL — unnecessary per-request presign cost/latency; (3) missing Cache-Control/immutable headers on served objects; (4) image variant pipeline: repeated processing, missing short-circuit when variant exists; (5) list operations in cleanup — full-bucket scans on a cron; (6) unbounded growth: no lifecycle/expiry for orphans, exports, variants; (7) per-request S3Client instantiation vs reuse (serverless cold-start cost). Set lens to "cost-perf".`,
  },
  {
    key: 'prod-readiness',
    prompt: BASE + `PRODUCTION READINESS. Check: (1) env validation: are ALL R2 vars validated at boot (0.validate-env.ts) — missing var behavior in prod (crash vs silent broken uploads); (2) config drift dev/prod: hardcoded bucket names/URLs, assumptions that only hold in dev (e.g. empty QSTASH token fallback affecting imageVariant), the known shared dev/prod bucket TODO — is anything in code making it worse (key collisions between envs); (3) CORS assumptions: does the presign flow require bucket CORS that code comments/docs don't document; (4) size-limit coherence: nuxt-security 5MB upload vs Zod schema limits vs presign content-length pinning vs R2 — contradictions; (5) observability: are R2 failures captured (Sentry) or swallowed; can ops tell bucket outage from bad request; (6) docs: is required bucket setup (CORS, lifecycle) written down anywhere. Findings that require Cloudflare dashboard action are still findings — mark them in recommendedFix as "operational follow-up". Set lens to "prod-readiness".`,
  },
  {
    key: 'e2e-flow',
    prompt: BASE + `END-TO-END FLOW as one state machine: presign → client upload → confirm → url.get → delete → GDPR purge → cleanup cron, plus the direct upload path and the dataExport path. Walk every transition and hunt gaps BETWEEN steps that sectoral lenses miss: (1) rows stuck in pending/unconfirmed forever — who cleans them and when; (2) double confirm / confirm after delete; (3) delete racing imageVariant generation; (4) GDPR purge vs files shared by dedup with a surviving org; (5) dataExport lifecycle: export object orphaned if the claim/notify step fails, expiry of the download link vs object retention; (6) cleanup cron deleting objects that a concurrent confirm just claimed. For each finding name BOTH sides of the race/gap with file:line. Set lens to "e2e-flow".`,
  },
]

phase('Find')
const reviews = (await parallel(LENSES.map(l => () =>
  agent(l.prompt, { label: `find:${l.key}`, phase: 'Find', schema: FINDINGS_SCHEMA })
))).filter(Boolean)

// Barrier justified: dedup needs ALL lenses' findings at once (spec phase 3).
const merged = new Map()
for (const r of reviews) {
  for (const f of r.findings) {
    const key = `${f.file}#${Math.floor(f.line / 15)}`
    const prev = merged.get(key)
    if (prev) {
      prev.lenses.push(r.lens)
      const order = { P0: 0, P1: 1, P2: 2, P3: 3 }
      if (order[f.severity] < order[prev.severity]) prev.severity = f.severity
      prev.duplicates.push({ title: f.title, lens: r.lens, description: f.description })
    } else {
      merged.set(key, { ...f, lenses: [r.lens], duplicates: [] })
    }
  }
}
const deduped = [...merged.values()]
const rawCount = reviews.reduce((n, r) => n + r.findings.length, 0)
log(`${deduped.length} unique findings from ${rawCount} raw`)

phase('Verify')
const ANGLE_TEXT = {
  correctness: 'CORRECTNESS: is the claimed behavior actually what the code does? Read the exact files and lines cited. Check the claim against the real control flow, not the finding\'s paraphrase.',
  exploitability: 'EXPLOITABILITY / REPRODUCIBILITY: can the failure scenario actually happen given auth middleware, validation, config, and callers? Trace the full request path from route to provider.',
  impact: 'IMPACT: is the severity justified? What is the real blast radius (data loss? cross-tenant read? cost only?). Downgrade or upgrade severity with evidence.',
}
const verifyPrompt = (f, angle) => `You are an adversarial skeptic. A code review of the R2 storage integration produced the finding below. Your job is to try to REFUTE it with code evidence.

${CONTEXT}

FINDING:
${JSON.stringify(f, null, 2)}

YOUR ANGLE — ${ANGLE_TEXT[angle]}

Read the actual files with the Read tool. Verdict "confirmed" ONLY if the finding survives your attack; "refuted" if the code already handles it or the scenario is impossible; "uncertain" if code alone cannot decide (e.g. depends on bucket config). If confirmed but the severity is wrong, set adjustedSeverity.`

const verified = await parallel(deduped.map(f => () => {
  const highSev = f.severity === 'P0' || f.severity === 'P1'
  const angles = highSev ? ['correctness', 'exploitability', 'impact'] : ['correctness']
  return parallel(angles.map(a => () =>
    agent(verifyPrompt(f, a), { label: `verify:${f.file}:${f.line}`, phase: 'Verify', schema: VERDICT_SCHEMA })
  )).then(votes => {
    const vs = votes.filter(Boolean)
    const nConf = vs.filter(v => v.verdict === 'confirmed').length
    const nRef = vs.filter(v => v.verdict === 'refuted').length
    let status
    if (highSev) status = nConf >= 2 ? 'confirmed' : (nRef >= 2 ? 'refuted' : 'uncertain')
    else status = vs[0] ? vs[0].verdict : 'uncertain'
    const adj = vs.filter(v => v.verdict === 'confirmed' && v.adjustedSeverity).map(v => v.adjustedSeverity)
    const severity = (adj.length && adj.every(s => s === adj[0])) ? adj[0] : f.severity
    return { ...f, severity, status, votes: vs }
  })
}))

return {
  lensVerdicts: reviews.map(r => ({ lens: r.lens, verdict: r.verdict, rawCount: r.findings.length })),
  confirmed: verified.filter(f => f.status === 'confirmed'),
  uncertain: verified.filter(f => f.status === 'uncertain'),
  refuted: verified.filter(f => f.status === 'refuted'),
}
```
